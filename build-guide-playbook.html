The release to build guide playbook for dev tools

How to turn a release into a build guide

The format behind the build guides of dev tool companies growing their traffic

Read the guide Copy the template

Most dev tool companies ship far more than they ever explain. A release goes out with a changelog line, and nobody shows a developer how to build something with it.

We looked at the dev tool companies whose search traffic grew over the last year, read their build guides from start to finish, and compared them with everyone else’s.

TL;DR

  • How often matters more than how. Companies growing their traffic turn about four times as many of their releases into build guides as companies whose traffic fell.
  • Their guides share a shape. They start from a job the reader wants done, run about six steps with code in each, link to the docs, and end with a short FAQ and a free signup.
First

What counts as a build guide

A build guide takes one release and walks a developer through using it to get something real working.

Could a reader follow it from start to finish and end up with something that works?

About a quarter of the posts that look like build guides fail that test on a full read. These are the usual suspects:

Webinar recapsThe building only happens in the recording
Prompting tipsChecklists and advice, nothing to build
Tools roundupsA list, not a walkthrough
Problem explainersOne code sample, no steps

They’re all useful posts. They’re just not build guides.

Step 1

Pick the release

Choose a release that lets someone build or do something new. Start with launches, since each one is more likely to be worth a guide, then add features that open up something new to build. Growing companies turn more of both into guides.

If all a guide could say is “turn this setting on”, it’s a docs line, not a guide.

Step 2

Pick the job, not the feature

Decide what the reader is trying to get done: “route alerts to the right team”, not “our new Rules Engine”.

What we found
94%of guides at companies with growing traffic start from a job
Step 3

Pick the type that fits

Growing and flat companies use the same mix of types, so no type wins. Choose by fit.

TypeWhat the reader does
Feature setupUses the new feature inside your product
IntegrationConnects it to a tool they already use
Project buildBuilds a small working thing from start to finish
MigrationMoves from the old way to the new one
Step 4

Write the guide, part by part

Eight parts, in this order. The numbers compare guides at growing companies with guides at flat ones.

1 / Title

Name the job and the result

  • Shape: “How to [do the job] with [release or product]”.
  • Name the result the reader gets. About three in four titles do, in every group.
  • Lead with the job, not a list of tools. Growing companies name another tool in the title less often (45% against 68%).
2 / Opening, about 150 words

Start with their problem

  • The reader’s problem first, in their words.
  • One sentence on what they’ll have working by the end.
  • The release or version it covers.
3 / What you need first

A short list, before step one

Accounts, versions, API keys and anything to install. Short and bulleted.

4 / The steps, about six

Code in every step

Each step gets a heading that says what it does (“Step 3: Create the triage rule”), one or two sentences on what and why, a code block or command, the expected output where it helps, and a link to the matching docs page.

5 / Show the result

Prove it works

An output, a screenshot or a short demo of the finished thing.

6 / Where people get stuck

Be honest about the limits

The two or three places readers trip up and how to get past them, plus what the release doesn’t do yet.

7 / FAQ, three to five questions

Questions about the job

Questions people really ask about the job, not about your company. Two or three sentences each.

8 / Close

What next, and a way in

One line on what to build next, a free signup or trial if you’re self-serve (sales if you’re not), and a link to the full docs.

Then

Write them often

A good format published once a year won’t close the gap. The biggest difference between growing companies and the rest is how often they write them.

What we found
4×as many releases turned into build guides at companies growing their traffic
Nearly halfof the companies whose traffic fell never turned a single release into a deeper post

If you ship every week, one guide a month from your biggest release puts you ahead of most dev tool companies.

And

It has to be a build guide

When companies whose traffic fell do write a deeper post, it’s rarely a build guide. They write comparisons just as often as growing companies, and far more use cases with code: a release shown in a single example, with no walkthrough. Growing companies write the build guide.

So a code sample or a comparison won’t stand in for the guide. If a reader can’t follow it from start to finish and end up with something working, it’s a different kind of post.
